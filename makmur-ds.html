Autocomplete / Search

Interactive Demo

Behaviour

Third characterThe panel opens. Nothing happens at one or two — the threshold stops a query firing on every keystroke.
While resolvingLoading State holds the panel open at full height, so the list does not jump when results land.
Typing pausesEach keystroke restarts a 250ms wait, so one query fires per pause rather than one per character.
A slow responseResults that arrive after a newer keystroke are discarded, so an answer to "BB" can never overwrite one to "BBRI".
Matched charactersThe part of each result that matches what was typed is emphasised.
Nothing matchesThe panel shows the Error state, which quotes the query back and suggests checking the spelling. It holds nothing to choose, so clicking it dismisses, and returning to the field does not bring an empty panel back. Error is a result, not a content type — so it is reached by searching, not by a switch.
Click or Enter a rowIts label is written into the field, the panel closes, and the row becomes the committed value.
Return to the fieldThe panel reopens against the same query without refetching, and the committed row shows in Selected.
Edit the queryThe committed value is dropped and a new query resolves. A changed query always refetches; an unchanged one never does.
Click away, or EscapeBoth abandon the edit. Whatever has been typed is discarded and the last committed value returns; if nothing was ever chosen the field empties. The panel closes and anything still in flight is dropped rather than allowed to land later. Leaving the field is not a way to commit a query nobody picked — only choosing a row sets the value.
Arrow keys, Home, EndMove one highlight through the options. Pointer and keyboard share it, so hovering moves what Enter would take. It borrows the Hover treatment, because no keyboard-active variant exists.
Screen readersThe field is a combobox and the panel a listbox; the active row is announced as you move, and the number of results is read out when they land.

Findings

The pattern has eight states and no defined behaviourMedium

Between them the two sets publish every state this pattern needs — rest, loading, results, grouped, error, hover, selected. What no artefact in Figma records is the sequence that moves between them: when the panel opens, whether a query refetches, what a selection does to the field, what dismissing leaves behind. Those are the decisions an engineer has to make to ship it, so right now each implementation invents them and they drift. The behaviour table above the Properties section is a first draft of that contract — worth agreeing and then writing into the component description, where it travels with the component instead of living in whoever built it last.

Search and the Dropdown are focus and hover mirror imagesHigh

Search publishes a Focused variant and no Hover. The Dropdown publishes Hover and no Focus. Between them they cover both states, but neither covers both — so a search field gives no pointer feedback and a results list gives no keyboard indicator. Button and Button Group sit on the Dropdown's side of that split, publishing Hover and never Focus, which leaves Search as the only component in the whole section that tells a keyboard user where they are. This is the one finding in the audit with an accessibility consequence rather than a consistency one.

The field and its panel are two unrelated sets, 180px apart in widthMedium

Search is 220px wide. Dropdown - Search & List is 400px. Nothing in either component references the other — no boolean for an open panel, no shared width, no slot. Every autocomplete in the product is therefore two instances stacked by hand, and the results panel is nearly twice the width of the field it drops from. That may well be deliberate, but because it is assembled per screen rather than published as one component, nothing holds the offset, the gap or the alignment steady between screens. Composing them into a single set with the panel as an optional slot would fix the drift and give the pattern one name.

Search's state model contradicts itselfMedium

State=Enabled, Disabled=True is a selectable combination — two properties describing the same thing in opposite directions, and the file ships three variants in exactly that state. Renaming the State values to describe interaction (Rest, Focus) rather than availability resolves it. The same property is spelled Disabled here and Disable on both Button components, so the section disagrees with itself on one of its most common properties.

Dropdown collapses content type and interaction stateMedium

Default, Hover, Selected, Error and Loading State describe what the list is doing. RD Select, Saham Select and Grouped describe what the list contains. All eight are values of one State property, so a grouped list can never also be hovered and a Saham list can never show an error. Splitting into Content and State gives you the combinations the product actually needs without drawing them individually.

Findings

The size scale is off by one stepHigh

Button publishes at 40 / 36 / 32. Button Group and Search both publish at 44 / 40 / 36. So Button's largest size is the same height as everyone else's medium, its smallest has no counterpart anywhere, and it has no 44px variant at all. A Large Button Group beside a Big Button in the same toolbar is 44 against 40. This is invisible while you work inside a single component sheet and only shows up once controls sit side by side in a real screen — which is also why it tends to get patched per screen with manual overrides rather than fixed at the source.

Hover is published, focus is notHigh

Button publishes a Hover variant and no Focus variant. Whatever the browser draws by default is therefore what ships, which on a #0C0D0E ground is frequently invisible. Button Group has the same gap; Search is the only component in the section that publishes a Focused state, and it publishes no Hover — the two are exact mirror images of each other. Of everything in this audit, this is the finding with an accessibility consequence rather than a consistency one.

Four property names break convention, each differentlyMed

Tipe is Bahasa where every other property on this component is English. Transparant is misspelled, and it appears in four of the nine colour options. Disable is the verb where Search uses the adjective Disabled. And Big/40, Med/36, Small/32 bake pixel values into the value names, which no sibling does and which guarantees the name goes stale the moment a height changes. Worth settling as a written convention before the remaining nine pages in the section harden.

A pressed-state token exists that no component usesMed

Turquoise T12 #172022 is documented on the colour page as "Click button", and T13 #195E57 as "Disabled". T13 is in use; T12 is not — no component in this section publishes a pressed or active variant at all. The decision about what a press looks like was made, written down as a token, and never reached a component. The playground above uses T12 for its pressed state to show what that decision looked like.

Sell has no disabled state, at any size or styleHigh

Every dashed cell in the Disable column above sits in a Red row. Green publishes 48 variants plus three disabled-and-loading; Red publishes 36 and stops. There is no way to show a disabled Sell button, which in a trading product is exactly the state you need when an order cannot be placed — insufficient balance, market closed, suspended counter. It gets built by hand on the screen that needs it, outside the library, where nothing keeps it in step.

One decision is encoded in two propertiesMedium

Tipe=Buy always pairs with a /Green colour and Tipe=Sell always with /Red, so the colour axis carries no information the trade side does not already carry. Type/Color is also doing double duty in a second way: seen side by side, Soft is a 15% tint, Outline is the same colour as a border, and Transparant is the colour with nothing behind it — all three are the same decision about emphasis, bundled with hue. Separating emphasis from colour, and deriving colour from Tipe, collapses the set substantially and gives Sell its missing states for free.

Six variants describe a state that cannot happenMedium

The Disable + Loading column is empty everywhere except Transparant/Green and Transparant/White. A button that is simultaneously disabled and loading is not a state anyone designs for. Transparant/White is stranger still: it appears nowhere else in the set — no Default, no Hover, no Disabled, no Loading of its own — so a whole colour option exists only inside an impossible state. Both look like artefacts of duplicating variants rather than decisions.

Variants

Findings

Nothing records which segment is liveMedium

Dual and Triple publish five properties and none of them says which segment is on. Every variant in the file is drawn with the first segment active, so a designer needing the second or third has to reach inside the instance and override the layers by hand — which detaches those fills from the library and quietly opts that instance out of any future update. Customize does not have the problem, because Tipe Oder doubles as the answer there: Buy lights the left block, Sell the right. Giving Dual and Triple an equivalent property — an index, or one boolean per segment — would close the gap and make the set describable in code.

Hover is published, focus is notHigh

Button Group publishes a Hover variant and no Focus variant — the same gap Button has. A segmented control is reached by keyboard more often than a plain button, since moving between segments is the whole interaction, so the missing focus indicator costs more here than it does on Button. Search is the only component in the section that publishes a Focused state.

The order-side property is Bahasa and misspelledMed

Tipe Oder should be Tipe Order, and sits beside Size, State, Type and Disable in English. Button has the same mixed-language problem under a different name — Tipe — so the two components disagree with the convention and with each other. Renaming both to one English property applied consistently would also make the Buy/Sell axis searchable in the insert menu.

A variant carries the wrong TypeHigh

The variant published as Size=Large, State=Default, Type=Dual, Disable=False, Tipe Oder=Sell is 326px wide. Dual variants are 382px and Customize variants are 326px, and on the canvas it sits inside the Customize block between the Large Customize Buy variant and its Hover twin. The geometry and the position both say Customize; only the property says Dual. Anyone switching a Customize group to Sell lands on a variant that reports itself as something else, and any code generated from these names inherits the error. Worth opening in the file to confirm before renaming.

Only Customize carries Buy and Sell, and none of them disableMedium

Dual and Triple are published exclusively with Tipe Oder=Default, so trade-side colouring is available in one of the three forms. And every disabled variant across all three forms is Default — the same gap Button has, reached by a different route. A disabled Buy or Sell group cannot be assembled from the library at any size.

Findings in Color

Five opacity tokens collapse to two colors on exportHigh

T10 (Secondary) and T11 (Hover) are documented as #00A88C at 15% and 25% — but opacity lives on the layer, not in the style, so both resolve to #00A88C, identical to T09. Same in Red: R06, R07 and R08 all resolve to #FF586C, identical to R03. Anyone exporting tokens or reading values through the API gets five duplicates and loses every state distinction. Bake the alpha into the token — rgba or an 8-digit hex — and they survive the trip to code.

The Blue board documents Purple's hexHigh

The Blue board lists B08 as #9860FF — that is Purple's P08 value. The published Blue/B08 style is actually #1B4F8B. The board was duplicated from Purple and the color code was never updated; P01–P07 rows from that duplication are still sitting in the layer tree behind the two visible rows. A designer reading the documentation and hand-entering that hex ships the wrong color.

Token architecture is split mid-migrationMedium

Everything here is published as styles. Only two variables exist — BW18 (DM - CARD 2) and BW21 - BG Tooltip — in a collection named "Variable collection". Given the page is called COLOR VARIABLE, the intent was clearly to move to variables; two tokens in means the migration stalled at the start. Variables are also what would let you express light and dark as modes rather than as (DM) suffixes scattered through the names.

Three pairs of indistinguishable greys, one undocumentedMedium

BW13 (Line focus state) and BW17 (Hover) are both #27292F — focus and hover render identically. BW10 #18191C and BW14 #18191A differ by two units in one channel; BW04 #DADADA and BW05 #D6D6D6 are equally close, as are Purple's P04 #AA89FA and P05 #A884FF. BW17 also has no hex printed on the page at all — only a note reading "Untuk hover" — so its value is discoverable only by inspecting the style.

Roles are documented in prose, not in tokensMedium

The Notes column carries real semantics — "Warna utama, button, uptren" on T09, "down tren" on R03, "Untuk warning" on Y05, "Error row table" on R08. That knowledge lives only on the page, in Bahasa, where no tool can read it. A developer picking Red/R01 has no way to know it is not the error color. Role-named aliases pointing at the hue ramp would carry these decisions into code.

"NEW" is baked into five permanent token namesLow

BW14 - NEW, B09 - NEW, T12 - NEW, T13 - NEW, R08 - NEW. A temporary status has become part of the name, so it will read as new indefinitely and any code generated from these names inherits it. BW20 has a related problem: the page notes call it a table row line, while the published style is named BW20 (DM - Text Field).

Findings in Type

Subtitle is documented but never publishedHigh

The typography page defines a full Subtitle ladder — 16/22, 14/20, 12/18, 10/18, all Semibold. None of it exists as a published text style; the library carries only Heading/H1–H8 and Body/B1–B8. Every subtitle in every screen is therefore detached type that no library update can reach. Conversely Body/B8 is published with nothing documenting it, so the page and the library disagree in both directions.

Two steps break the ladderLow

BODY 4 is 16/26 while BODY 3 above it is 18/24 — the line height grows as the size shrinks, which no other step in any of the three ladders does. SUBTITLE 3 and SUBTITLE 4 share a line height of 18 at 12px and 10px, so the smaller step is proportionally much looser than its neighbours.

Two distinct component sets are both called Button Group. Elsewhere: Dropdown Watchlist vs Dropdown - Watchlist, Table grid market vs market table grid, Tab Market vs Tab Market New.
